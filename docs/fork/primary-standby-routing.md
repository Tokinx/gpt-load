# 分组主备路由：行为与上游同步边界

## 使用规则

- 仅分组有 `priority_manual`，范围 1–100，越大越优先；`null` 使用默认 50。
- 先筛除权限不允许、禁用、黑名单、冷却、权重为零、模型不可用等候选，再比较分组优先级。
- 在当前路由层，只选最高可用分组优先级；该层所有分组的可用凭据继续使用上游权重调度，不增加凭据优先级。
- 这一层全部不可用或在本次请求中已尝试，才选下一层；恢复后，新请求重新优先选主层。
- 同层有效权重为 `分组权重 × 凭据权重`。权重不决定主备，不保证短窗口内严格流量比例。
- Preferred Credential 只在当前主层内生效；显式同凭据认证刷新重放仍沿用上游合同。
- 分组优先级全部未设置时，保持上游权重调度行为。

例如：分组 A 优先级 90、分组 B 优先级 50。A 有两把可用凭据时，只在这两把之间按权重分配；A 全部不可用或已尝试，才使用 B。不是 A 90% / B 50% 分流。

同一渠道需要多个主备层时，创建多个分组并配置不同凭据即可。不要将同一凭据重复配置成备用，以免形成虚假的故障隔离。

## 保留上游路由合同

完整顺序：存储语义正常路由优先于存储降级路由 → 上游路由模式层 → 分组优先级降序 → 同层有效权重公平调度。

`native_first` 下先原生再转换；`weighted_mix` 下原生/转换同层。若要跨原生/转换路径按手工优先级主备，需要选择 `weighted_mix`。优先级不会越过协议/操作准入、访问密钥权限及冻结的凭据身份限制。

重试次数、错误是否允许重试、并发准入和健康冷却仍由上游处理。不可重试错误或重试预算耗尽时，不保证继续使用备用。

Inspector 的 `available` / `routable` 表示资格，`active` 表示当前参与调度；备用不是故障。这是查询时快照，不是运行时所有重试结果的承诺。

## 维护边界

基线：`82036b36`（2026-09-30 从 origin 拉取并快进同步，包含 #793）。原始分支保存在 `backup/group-credential-priority-20260930`；收敛前两级版本的 stash 快照保存在 `backup/two-level-priority-before-group-only-20260930`。

- `internal/scheduler/routing_policy.go` 集中定义优先级比较，调度器和 Inspector 共用。
- 候选资格过滤之后、公平调度之前加入分组优先级过滤；保留 `fair.go` 上游算法。
- 数据模型、loader、快照、分组 API 和两套 UI 传递/校验分组优先级。凭据 registry、运行时视图、配置 API 和编辑组件保持上游实现。
- `0024_priority_manual` 仅创建分组优先级，不重写初始 schema。旧数据库若有 `credentials.priority_manual`，列和数据保留但不再读取；新数据库不创建该列。
- 历史 fork `0021/0022/0023_priority_manual` 及 `#building` 标记按精确白名单清理，再执行缺失的上游迁移及当前迁移。不能跳过上游 `0023_access_key_concurrency`。

### 每次同步上游

1. 先备份分支和数据库，检查迁移编号。0024 不是永久预留编号；若上游占用，必须重编号并追加精确旧 ID 兼容测试，不能只改文件名。
2. 检查候选收集、路由层次、亲和、身份冻结和公平调度边界；自动合并成功不代表语义正确。
3. 执行 `go test ./...`、`go vet ./...`；发布工作流测试还需要 Python 3.10+。
4. 在 web 使用锁定依赖，执行 type-check、lint、build 和 Inspector display tests。
5. 验证全新数据库、历史 fork 账本（含 building）、主层失效/恢复、同层权重，以及 Inspector 与调度一致。
6. 在数据库副本上演练升级后再部署；单元测试不等于已验证生产升级。

## Fork 镜像与部署

`feat/group-priority` 推送触发独立的 `Docker Image` 工作流，发布到
`ghcr.io/tokinx/gpt-load:group-priority`，同时发布完整提交 SHA 标签。
上游 Release 工作流与 `latest` 标签保持不变。只有 CI 成功且对应镜像已发布，才能用该标签部署。

Compose 可直接引用远程镜像，无须重新打标签为 `gpt-load:local`：

```yaml
services:
  gpt-load:
    image: ghcr.io/tokinx/gpt-load:group-priority
```

升级前保留旧镜像，并在停止写入后备份数据目录、密钥和 Compose 配置；先在数据副本演练迁移。
拉取镜像后核对 `org.opencontainers.image.revision` 与预期提交，再重建并验证健康接口、版本与数据库完整性。
涉及数据库升级的回滚需要同时恢复备份数据，不能仅切换旧镜像。

Dockerfile 保持基础镜像版本和 digest 固定，对 OpenSSL 强制不低于 `3.5.8-r0` 的安全版本下限，
允许 Alpine 同一发行版中的更新补丁。不要锁死滚动软件源可能已移除的补丁包，也不要为通过构建降级安全依赖。
